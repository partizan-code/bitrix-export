# Правила работы с репозиторием

## Рабочий процесс

- Общение, документация и новые комментарии — на русском; команды и идентификаторы
  сохраняют принятые названия. Назначение проекта — в [README.md](README.md),
  техническая документация — в [docs/](docs/README.md).
- Определяйте режим до действий: DEVELOPMENT — явно разрешённое изменение файлов;
  REVIEW / ANALYSIS / PLANNING — только чтение, тесты лишь по явному запросу
  и при проверенной изоляции. Обсуждение исправления не разрешает реализацию.
- Читайте применимые `AGENTS.md` и существующий `PROJECT_STATUS.md`. Перед
  разработкой проверяйте корень Git, ветку, upstream и все локальные изменения.
  Сохраняйте ветку и чужие правки; не делайте авто-stash и очистку.
- Синхронизация Git допустима только при разработке: `fetch`, при чистом дереве
  и безопасном fast-forward — `pull --ff-only`. Staging, commit и push — только
  по явному разрешению. Не создавайте upstream и не переключайте ветку сами;
  запрещены force-push, автоматический `reset --hard`, потеря локальных правок
  и переписывание опубликованной истории.

## Принципы проекта

- `actor` — фактический участник касания; `responsible_user_id` — ответственный
  за сущность. Не подменяйте одного другим.
- Накопительный снимок строится с использованием `data/store/` и
  `data/registry.json`. Не удаляйте их и не меняйте политику
  `REEXPORT_CLOSED_ON_CHANGE` без причины. Технические сущности отделяйте
  от проигранных продаж.
- Общую логику сделок и лидов параметризуйте через `_ENTITY` / `entity`.
  Сохраняйте плоские модули, Python 3.12, `venv/`, `requirements.txt` и стандартный
  `logging` (`b24`). Не вводите пакетную структуру, mise/uv, зависимости или
  другой стек логирования без соответствующей задачи.

## Код, проверка и документация

- Меняйте только относящиеся к задаче файлы. Настройки — в `config.py`.
  Python-модули начинайте с русского docstring;
  предпочитайте функции и словари, ID из API приводите к `int`.
- Bitrix24 вызывайте через `B24Client`; прямой `requests` — только для файлов
  и AssemblyAI в `transcribe.py`. Сохраняйте тайм-ауты, повторы и обработку
  ошибок отдельных сущностей без остановки всего прогона.
- Файлы — UTF-8, JSON — `ensure_ascii=False`. Новые/изменяемые записи делайте
  атомарно (`tmp` + `os.replace`, для аудио `.part`); не считайте все текущие
  записи уже атомарными.
- Новый источник проводите через `normalize.py`, рендер — через
  `export_llm.deal_markdown`; согласуйте схему и затронутые страницы `docs/`.
- Изолированные тесты `unittest` — в `tests/`, запуск и изоляция описаны
  в [docs/testing.md](docs/testing.md); CI нет. Примеры
  прогонов в [docs/setup.md](docs/setup.md) вызывают живой API и пишут данные.
  Нужны явное разрешение на цель/операцию либо изолированные данные и моки.
  Не запускайте устаревший `my_test.py`; reviewer — только по явному запросу.
- После изменения Python выполняйте доступные релевантные Ruff-проверки,
  не устанавливая инструменты ради проверки документации.
- После любых правок проверяйте актуальность документации и при необходимости
  обновляйте её в рамках той же задачи. Отражайте изменения поведения, настроек,
  команд запуска, зависимостей, форматов данных и интерфейсов в соответствующих
  разделах README и `docs/`; удаляйте устаревшие описания и примеры.
- Правила храните здесь, обзор — в README, технические сведения — в docs.
  У каждой темы должно быть одно основное описание; обновляйте относительные
  ссылки при переносах. `wiki/` отсутствует. Существующий `PROJECT_STATUS.md`
  обновляйте после существенной разработки; новый без согласования не вводите.

## Безопасность и завершение

- Не читайте `.env` без необходимости, не выводите секреты и авторизованные URL.
  Прямой режим транскрибации передаёт ссылку Диска AssemblyAI.
- Не коммитьте секреты, выгрузки, переписки, аудио, кэши, логи, базы и окружения;
  проверяйте diff/staged перед публикацией. Production API/БД и миграции требуют
  явного разрешения; при риске потери данных согласуйте резервирование и откат.
- В итоговом отчёте укажите режим/область, результат, выполненные и пропущенные
  проверки, Git, риски и следующие шаги. Не заявляйте о невыполненных действиях.
