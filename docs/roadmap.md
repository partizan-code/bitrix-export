## Ускорение выгрузки Bitrix24 и транскрибации

Добавлено 23 ноября 2026 года. Статус: запланировано; оптимизации пока не
реализованы. Выполнять отдельной задачей после проверки первого серверного
снимка. Текущую выгрузку не прерывать ради этих изменений.

### 1. Измерить затраты времени

- Добавить счётчики вызовов и замеры по методам Bitrix24: время HTTP-запросов,
  ожидание ограничителя частоты, число повторов и ошибок лимитов.
- Отдельно измерять скачивание аудио, загрузку файла в AssemblyAI, ожидание
  распознавания, переиспользование кэшей и финальную сборку снимка.
- Использовать монотонные часы; в логах сохранять агрегаты без секретов,
  авторизованных URL и содержимого карточек.
- По измерениям выбрать следующий этап и зафиксировать исходные показатели
  для сравнения. Не обещать ускорение всей выгрузки по одному значению паузы.

### 2. Учитывать время запроса в ограничителе частоты

Сейчас `B24Client.call` добавляет `REQUEST_PAUSE = 0.2` после каждого успешного
ответа. На 1000 успешных вызовов это 200 секунд дополнительных пауз.

- Заменить безусловное ожидание минимальным интервалом между началами запросов,
  учитывая уже затраченное время. Например, при интервале 0,55 с и длительности
  запроса 0,40 с оставшееся ожидание составляет 0,15 с.
- Применять единый ограничитель к вызовам клиента, включая повторы; сохранить
  обработку HTTP 429, `QUERY_LIMIT_EXCEEDED` и `OPERATION_TIME_LIMIT`.
- Согласовать бюджет запросов с тарифом и другими интеграциями на том же IP.
  Не уменьшать задержку вслепую; обновить описание настройки и команд проверки.

### 3. Объединить независимые запросы через batch

- Добавить поддержку `batch` в `B24Client`, проверив совместимость каждого
  используемого метода и ограничения Bitrix24.
- Начать с точечного добора `crm.activity.get`, когда `crm.activity.list`
  не возвращает `FILES`: сейчас каждый такой вызов выполняется отдельно.
- Сохранять соответствие результатов исходным ID, разбирать ошибки отдельных
  команд и повторять только неудавшиеся операции. Сохранять пагинацию и охват.
- Учитывать ограничения ресурсоёмкости: `batch` сокращает число HTTP-запросов,
  но не устраняет все ограничения API.

Официальные ограничения и допустимый размер пакета:
[REST API Limits](https://apidocs.bitrix24.com/settings/performance/limits.html).

### 4. Отделить аудио и распознавание от последовательного обхода

Сейчас обработка одного звонка ожидает скачивания, загрузки и результата
AssemblyAI до перехода к следующему звонку.

- Спроектировать очередь с ограниченной параллельностью и учётом лимитов
  Bitrix24 и AssemblyAI; число одновременных операций сделать настраиваемым.
- Переиспользовать существующие аудио и расшифровки, защитить кэши от
  одновременной записи и повторной обработки одной записи.
- Сохранить ограниченные тайм-ауты, обработку ошибок отдельных записей,
  освобождение ресурсов и корректную остановку работников очереди.
- Сборку касаний, запись store/state/registry и финального снимка согласовать
  с завершением очереди; сохранить actor, порядок событий и формат карточек.

### 5. Быстро отключать прямую передачу URL при сбое

При включённом прямом режиме сначала пробовать передать URL аудио в AssemblyAI.
Если этот способ не работает, переходить на загрузку файлом без повторения
долгого ожидания для каждого следующего звонка.

- Разделить короткий настраиваемый бюджет проверки получения аудио по прямой
  ссылке и штатный тайм-аут распознавания. Не использовать ожидание 900 секунд
  для обнаружения неработающей загрузки по URL. При реализации проверить,
  какие ответы и статусы API позволяют различить получение аудио, очередь
  и распознавание; длительное распознавание не считать ошибкой ссылки.
- При явной ошибке получения аудио сразу переходить на скачивание сервером
  и upload в AssemblyAI; при исчерпании короткого бюджета делать тот же переход.
- После первого такого сбоя отключать прямой режим для всех оставшихся
  записей текущего прогона. Следующие звонки сразу обрабатывать через файл,
  без новых попыток URL и без ожидания по 15 минут на каждой записи.
- Предусмотреть одну пробу прямого режима в начале следующего прогона,
  если он включён настройкой; повторные пробы внутри того же прогона не делать.
- Согласовать общее состояние режима с будущей очередью работников,
  учитывать уже созданные задачи AssemblyAI при переходе на файл, чтобы
  избежать дублирующего распознавания и лишних расходов.
- В логах показывать причину и момент переключения без авторизованных URL.
  Сохранить переиспользование кэшей и обработку ошибок отдельной записи.

### Критерии приёмки

- Изолированные проверки с моками API и времени подтверждают интервалы,
  повторы, частичные ошибки batch, работу кэшей и ограничение параллельности.
- Для прямого режима проверить успешную пробу, немедленную ошибку и короткий
  тайм-аут получения аудио, переход текущей записи на файл и отсутствие новых
  прямых попыток после сбоя до конца прогона. Отдельно проверить, что обычное
  ожидание распознавания не вызывает ложного отключения прямого режима.
- Состав снимка, формат карточек, полнота касаний и инкрементальное состояние
  сохраняются на сопоставимых синтетических данных.
- Ускорение оценивается по времени этапов и общей длительности на сопоставимом
  объёме; одновременно проверяются количество запросов, повторов и ошибок.
- Сравнение на рабочем портале требует отдельного разрешения на конкретный
  запуск; изолированные тесты не подменяют измерение реальной скорости.

## Пригодность SQL-выгрузки для финансового анализа

Добавлено 24 ноября 2026 года. Статус: запланировано; замечания зафиксированы
по результатам анализа выгрузки, предоставленным пользователем.

### 1. Разделить сумму сделки и валюту

Сейчас суммы сделок хранятся текстом, например `4691.80000000 BYN`, без
отдельного числового значения и самостоятельного поля валюты. Это требует
предварительного разбора строк для финансового анализа.

- Предусмотреть в SQL-выгрузке отдельные поля для точного числового значения
  суммы и кода валюты. Сохранять исходную точность; не использовать двоичную
  плавающую точку для денежных расчётов.
- Согласовать преобразование существующих значений, обработку отсутствующих
  и некорректных сумм, описание схемы и примеры аналитических запросов.
- В финансовых агрегатах учитывать валюту: суммы в разных валютах не складывать
  без явно заданных правил пересчёта.

### 2. Сохранить неопределённую страну

В проверенной пользователем выгрузке обнаружены 92 карточки со страной
`UNKNOWN`: 7 сделок и 85 лидов. Эти карточки нельзя автоматически приписывать
Беларуси или России.

- Сохранять `UNKNOWN` в SQL-выгрузке и выделять такие карточки в отдельную
  группу в аналитике по странам, без подстановки страны по умолчанию.
- Предусмотреть проверку источников страны и уточнение только при наличии
  подтверждающих данных; отсутствие сведений не считать основанием для
  отнесения к Беларуси или России.

### Критерии приёмки

- На изолированных данных значение `4691.80000000 BYN` выгружается как точная
  числовая сумма `4691.80000000` и отдельный код валюты `BYN`; финансовые
  агрегаты не требуют разбора текстового поля и учитывают валюту.
- Карточки с `UNKNOWN` сохраняют неопределённую страну и учитываются отдельной
  группой. На исходной проверенной выборке сохраняются 7 сделок и 85 лидов;
  эти числа описывают конкретную выборку, а не постоянное ограничение.
- Формат описаний в карточках сделок и лидов, включая подпись «Страна»,
  сохраняется; доработка касается SQL-представления и аналитики.
