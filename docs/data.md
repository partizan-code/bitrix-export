## Файлы результата

`entity` — `deal` / `lead`, `group` — `active` / `completed` / `technical`.

| Путь | Содержимое |
|---|---|
| `export/snapshot/{Сделки,Лиды}/{Активные,Завершенные,Технические}/` | Markdown-карточки; все шесть каталогов создаются даже пустыми |
| `export/snapshot/manifest.json` | Охват и результат сборки |
| `export/*.zip` | Содержимое snapshot, manifest в корне; пустые каталоги включены, `.DS_Store` / `._*` исключены |
| `data/sqlite3_snapshots.db` | Накопительная структурированная история конечных карточек ZIP; неизменные версии без повторов |
| `export/touchpoints_<entity>_<group>.jsonl` | Строка — касание; вне ZIP |
| `export/index_<entity>_<group>.jsonl` | Строка — индекс сущности; вне ZIP |
| `raw/<entity>_<id>.json` | Сущность и собранные источники для повторной нормализации |
| `audio/`, `transcripts/` | Кэши записей/текстов; `deal<id>_call<activity_id>.*` используется и для лидов |
| `data/store/` | Последние артефакты, структура ниже |
| `data/registry.json` | Реестр: ключ `<id>` сделки, `lead:<id>` лида |
| `data/state.json` | `last_run`, `export_id`, `export_type`, счётчики, `errors.deals/leads` |
| `data/progress.json` | Этап, счётчики, ошибки; в конце итог и имя ZIP |
| `data/deal_fields_meta.json`, `data/lead_fields_meta.json` | Раздельные кэши метаданных, обновляемые общим загрузчиком атомарно |
| `data/*.json` | Кэши пользователей/контактов, стадий/статусов, источников, воронок, метаданных полей |

В store сделки лежат в `deals/<id>.md`, `tps/<id>.jsonl`, `index/<id>.json`,
`deal/<id>.json`; лиды — в тех же подкаталогах внутри `data/store/lead/`.
`store.has_deal` требует все четыре файла. Raw включает историю стадий,
нормализованные звонки, чаты и включённые источники, а не все ответы API.
Общей CLI-пересборки из raw нет; для имён — [scripts/refresh_names.py](operations.md#обслуживание).

Атомарность кэшей метаданных не означает атомарность всей выгрузки: четыре
файла store записываются последовательно, а state и registry — напрямую.
`has_deal` проверяет наличие файлов, не их читаемость или согласованность.
Порядок резервирования и проверки после обрыва — в
[инструкции эксплуатации](operations.md#хранение-и-безопасность).

Имена карточек:

```text
<BRAND>_DEAL_<CTRY>_<PIPELINE>_<ID>_SNAP_<YYYYMMDD>T<HHMMSS><TZ>_schema-v<N>.md
<BRAND>_LEAD_<CTRY>_<ID>_SNAP_<YYYYMMDD>T<HHMMSS><TZ>_schema-v<N>.md
```

Бренд — `FILE_BRAND`. Служебная страна (`_country`) используется в шапке
карточки (строка «Страна»), имени файла, индексе и `countries` manifest:

- Сделки: по ID воронки из `DEAL_COUNTRY_BY_CATEGORY` в config.
  `РБ OFF` (0), `РБ ON` (34), `РБ Отложенный спрос` (36) и
  `Кухни ON+OFF` (6) → `RB`; `Россия OFF` (28), `Россия ON` (32) и
  `РФ Отложенный спрос` (38) → `RF`. Переименование воронки не меняет правило;
  при добавлении воронки нужно обновить соответствие ID.
- Лиды: по началу расшифрованного `_source`: `РБ` → `RB`, `Россия` / `РФ` → `RF`.
  Регистр и крайние пробелы не учитываются; название должно начинаться
  с отдельного обозначения страны. У лидов нет воронки.
- Неизвестная воронка, пустой или нераспознанный источник → `UNKNOWN`
  и предупреждение в логе. Автоматической подстановки `RB` нет.
  `Рекрутинг и найм` и `Росмебель` не имеют соответствия страны;
  это правило само по себе не исключает их из выборки.

Исходное поле Bitrix «Страна» в JSON, `_fields` и разделе «Поля сделки» /
«Поля лида» сохраняет значение CRM (ID списка разрешается в его название).
Пустое поле не заполняется вычисленным значением; пустые поля, как и прежде,
не выводятся в разделе полей. Расхождение с `_country` допустимо.
Структура, подписи, порядок и оформление карточек сохраняются.

При переносе закрытых/технических сущностей из store служебная страна
вычисляется заново для текущего снимка: обновляются шапка, имя и индекс,
остальной текст карточки и исходные поля переносятся без изменений.
Старые файлы store при таком переносе не перезаписываются. Для лидов
используется актуальное название источника, при отсутствии его в справочнике —
сохранённый `_source` того же `SOURCE_ID`. `scripts/refresh_names.py` также пересчитывает
страну, сохраняя результат в store при обычном перерендере.

Один `ExportContext` задаёт время карточек, manifest и ZIP в `SNAPSHOT_TZ`.
`ZIP_NAME_TEMPLATE` использует `{stamp}` = `ГГГГ-ММ-ДД ЧЧ-ММ`: повторная сборка
в ту же минуту может перезаписать архив.

## SQLite

### База конечных карточек без повторов

Основной вариант — [snapshot_sqlite.py](../snapshot_sqlite.py) и
[parse_snapshot.py](../parse_snapshot.py). Источник данных — **только конечные
карточки и manifest внутри ZIP schema-v2**. Store, JSON/JSONL, метаданные CRM,
`.env`, аудио и сеть не используются. Формат карточек не меняется.

В обычном `sync.py` после сборки архива импорт включён настройкой
`SNAPSHOT_SQLITE_ENABLED=True`, путь — `SNAPSHOT_SQLITE_PATH`
(`data/sqlite3_snapshots.db`). Для ранее созданных архивов:

```text
mise exec -- uv run --locked python -B scripts/snapshot_sqlite.py "первый.zip" "второй.zip" --db data/sqlite3_snapshots.db
```

Пути относительны текущему каталогу. Архивы можно добавлять в любом порядке;
дата берётся из manifest. Повтор того же ID и содержимого пропускается,
перепаковка ZIP не создаёт новый слепок. Тот же ID с другим содержимым
отклоняется. `complete/partial` сохраняются, отсутствующие карточки не
дополняются из других архивов. Группы, количества и наборы ID сверяются с
manifest. Неизвестные файлы или неподдерживаемая структура вызывают откат,
а не частичное заполнение. Старый формат не поддерживается.

| Таблица | Содержимое |
|---|---|
| `snapshots` | ID, дата, часовой пояс и статус слепка, имя архива, отпечаток содержимого, исходный manifest, время импорта |
| `card_versions` | Уникальные версии полей сделки/лида **без ленты**. Основные колонки: `title`, `crm_url`, `responsible_name`, `client_name`, `stage_name`, `source_name`, `country`, `created_at`, `amount`. Дополнительные поля — отдельные текстовые колонки `field_<подпись из карточки>` |
| `events` | Уникальные версии касаний: `event_type`, `occurred_at`, `channel`, `actor_name`, `stage_name`, `text`; для звонков — `direction`, `duration_seconds`, `recording_file_ids`, `audio_filename`, `failure_code`, `transcript_status`; для задач — `task_title/status`, `deadline`, `closed_at`, `created_by`; для смены стадии — `stage_from/to` |
| `snapshot_cards` | Тип/ID карточки, группа и путь в конкретном ZIP, ссылки на версию полей и ленту, SHA-256 исходной карточки |
| `timelines` | Уникальные версии последовательностей событий карточки; неизменная лента целиком переиспользуется в следующих слепках |
| `timeline_events` | События конкретной версии ленты; `position` сохраняет исходную последовательность, включая одинаковые сообщения в одну минуту |
| `field_columns` | Соответствие подписи поля его SQL-колонке; повторяющиеся подписи различаются номером в карточке. Это не метаданные полей CRM |

Представление `snapshot_events` связывает слепки с событиями через версии лент,
не дублируя физически состав неизменной ленты для каждой даты.
Представления `cards` и `event_history` уже объединяют версии со слепками.
`responsible_name` — ответственный за карточку; `actor_name` — участник
касания. Они не подменяют друг друга. Коды полей CRM, скрытые ID участников
и сведения, отсутствующие в Markdown, не добавляются. Суммы и значения
дополнительных полей сохраняются в отображаемом виде; для арифметики их
следует явно преобразовывать. Отсутствовавшее поле — `NULL`, явно пустое —
пустая строка. При новом поле добавляется колонка; старые версии не меняются.
Одноимённые дополнительные и основные поля разделены, например `country`
и `field_Страна`. Нестандартные имена колонок экранируйте двойными кавычками.

Текст события сохраняется один раз, с исходными отступами и маркером
«Транскрипция:», если он был. `headline` содержит исходный заголовок без
временной метки. Небольшие сведения об оформлении (`layout_json`, разделители)
нужны для точного восстановления, полная текстовая копия карточки не хранится.
`restore_card(connection, snapshot_id, entity, entity_id)` восстанавливает
Markdown только из БД. **Перед фиксацией каждого слепка все его карточки
восстанавливаются и сравниваются с ZIP побайтно**, включая CRLF, многострочные
значения, порядок и повторы событий.

Неизменное событие или набор полей переиспользуется; изменившийся сохраняется
новой версией. Связи слепков остаются независимыми: исчезнувшее событие
не удаляется из предыдущего слепка. Устранение повторов работает внутри
одной сделки/лида; одинаковые тексты в разных карточках не объединяются.
`event_id` — внутренний ID **версии содержимого**, а не ID события Bitrix.
Из Markdown нельзя надёжно установить, является ли изменённый текст правкой
прежнего сообщения. Поэтому автоматического склеивания таких событий нет;
`COUNT(DISTINCT event_id)` за несколько слепков считает версии, а не гарантированно
уникальные звонки/сообщения. Активность надёжнее считать по одному выбранному
слепку, учитывая его охват; сравнение версий требует отдельной интерпретации.

`occurred_at` сохраняет местное время до минуты, как в карточке; пустое
время остаётся пустым. Секунды и индивидуальный часовой пояс события не
восстанавливаются. `snapshot_timezone` из manifest задаёт контекст выгрузки,
но не доказывает часовой пояс каждого исходного события. Одной временной
метки недостаточно для уникальности; порядок задаёт `position`.

Примеры запросов:

```sql
-- Карточки последнего слепка.
SELECT entity, entity_id, responsible_name, stage_name, amount
FROM cards
WHERE snapshot_id = (
  SELECT snapshot_id FROM snapshots
  ORDER BY julianday(snapshot_at) DESC, snapshot_id DESC LIMIT 1
);

-- Полная лента конкретной сделки на выбранную дату.
SELECT occurred_at, event_type, actor_name, text
FROM event_history
WHERE snapshot_id = :snapshot AND entity = 'deal' AND entity_id = :deal_id
ORDER BY position;

-- Звонки продавца в одном слепке. Имя автора берётся из касания.
SELECT actor_name, COUNT(*) AS calls, SUM(duration_seconds) AS seconds
FROM event_history
WHERE snapshot_id = :snapshot AND event_type = 'call'
  AND actor_name LIKE '%Селицк%'
GROUP BY actor_name;

-- Изменение полей сделки между слепками.
SELECT snapshot_at, responsible_name, stage_name, amount, "field_Страна"
FROM cards WHERE entity = 'deal' AND entity_id = :deal_id
ORDER BY julianday(snapshot_at), snapshot_id;
```

Каждый ZIP фиксируется отдельной SQLite-транзакцией, включая новые колонки;
при ошибке он откатывается полностью. Ранее импортированные слепки сохраняются.
Ожидание блокировки — 10 секунд. Чужие базы и предыдущие прототипы отклоняются
без миграции: используйте новый файл. Коды CLI: `0` — добавление/пропуск,
`1` — ошибка импорта, `2` — неверные аргументы. Если ошибка произошла при
первой записи, может остаться пустой файл БД.

БД содержит те же чувствительные сведения, что архивы, и исключена из Git.
Тексты не дублируются между слепками, но связи и новые версии увеличивают размер.
Сравнение размера с ZIP требует измерения: SQLite не использует ZIP-сжатие.
Перед копированием остановите писателей или используйте SQLite backup API;
простое копирование активной базы не гарантирует согласованность.
Автоматической загрузки на Диск, очистки ZIP и удаления старых слепков нет.

### Структурированная база из первоисточников

Предыдущий самостоятельный прототип; основной вариант выше использует ZIP.

[source_sqlite.py](../source_sqlite.py) использует схемы `store.py` и
`normalize.py`, не разбирает Markdown и не читает ZIP. Для каждого снимка
сохраняются исходные коды/значения полей, их расшифровки, ID участников,
полное время касаний и все вложенные данные нормализованного формата.
Это отдельная схема БД; база с полными текстами ZIP не мигрируется.

После завершения обычной выгрузки, когда писатели остановлены, из корня
проекта на сервере или на согласованной копии данных:

```text
mise exec -- uv run --locked python -B scripts/source_sqlite.py --data-dir data --export-dir export --manifest export/snapshot/manifest.json --db data/sqlite3_structured.db
```

Все пути обязательны; относительные считаются от текущего каталога.
Нужны **данные одного завершённого запуска**:

- `export/snapshot/manifest.json`;
- `data/registry.json`;
- `data/store/deal/<id>.json` для сделок и `data/store/lead/deal/<id>.json` для лидов;
- `export/index_<entity>_<group>.jsonl` и `touchpoints_<entity>_<group>.jsonl`
  для непустых групп manifest;
- `data/deal_fields_meta.json` и `lead_fields_meta.json` для присутствующих типов.

Markdown store, raw, аудио, `.env` и настройки приложения не нужны.
Индекс и касания берутся из **текущих групповых JSONL экспорта**, а не из
старых файлов store: при переиспользовании закрытых сущностей в них уже
учтены текущая группа и пересчитанная страна. Полные исходные поля берутся
из JSON сущности в store. Лента читается потоком в порядке `deal_id`,
который формирует `sync.py`; сортировка по времени внутри сущности сохраняется.
Скрипт не обращается к API, не меняет источники и пишет результат только в
указанную БД; сообщения выводятся в терминал. Выбранные ID/группы берутся из
manifest. Из реестра проверяются ID снимка и группы; недостающие источники
не подменяются данными из ZIP. Проверяются ID сущностей, согласованность
полей индекса/сущности, число касаний, ID владельца и повторы ID касаний,
итоговые количества и наборы ID в группах manifest. Registry не доказывает
атомарность store: перед копированием остановите писателей и копируйте
весь согласованный комплект. Текущий store не восстанавливает старые недели.

| Таблица | Содержимое |
|---|---|
| `snapshots` | ID/дата снимка, `status`, `is_complete`, версия схемы данных, время импорта UTC, отпечаток источников, полный manifest |
| `entities` | Одна сделка/лид в снимке. Общие колонки: тип/ID, группа, заголовок, ответственный (ID и имя), клиент, стадия, страна, источник. Каждое поле JSON — отдельная колонка `raw_<CODE>`, расшифровка из `_fields` — `display_<CODE>`, исходная подпись — `label_<CODE>`; индекс — `index_<key>` |
| `field_definitions` | Для каждого снимка, типа и кода поля — название, тип, имена колонок и полные метаданные поля, включая варианты списков |
| `touchpoints` | Отдельные касания: `touchpoint_id`, `timestamp`, `channel`, `event_type`, `direction`, `actor__user_id`, `actor__name`, `responsible_user_id`, `content__text`, `content__duration_sec`, параметры задач, стадий и источников |
| `field_items` | Элементы массивов/объектов с путём, типом и значением, включая множественные поля и `source__file_ids` |

Ключ сущности — `(snapshot_id, entity, entity_id)`; ключ касания добавляет
`position`, то есть порядок источника. `touchpoint_id` сохраняется отдельно.
`actor__user_id` — фактический участник, `responsible_user_id` — ответственный;
один другим не подменяется. Вложенные объекты касания разворачиваются
колонками через `__`: например, `content.duration_sec` → `content__duration_sec`.
Новые поля добавляют колонки; у прошлых снимков они остаются `NULL`.
Числовые ID преобразуются в `int`; суммы, пришедшие строками, не округляются.
`NULL`, пустые строки, ноль и false сохраняются (SQLite хранит bool как 0/1).
Массивы и объекты полей также остаются JSON в своей колонке и дополнительно
разложены в `field_items`; текст целой карточки в этой схеме не используется.

Повтор снимка с теми же источниками пропускается; изменённые данные при том
же `export_id` вызывают конфликт. Изменение источников между двумя проходами
чтения отменяет импорт. Снимок, новые колонки и строки записываются общей
транзакцией, при ошибке откатываются. Неизвестные схемы БД не меняются;
тайм-аут блокировки — 10 секунд. Частичный CRM-снимок сохраняется как
`partial`, успешность записи в SQLite не превращает его в полный.
Источники нужно сохранять отдельно для каждой недели либо импортировать
в БД до следующего изменения store. Экспорт пока запускается вручную,
`sync.py` и бот его не вызывают.

Пример небольшой выборки для ИИ без передачи целых карточек:

```sql
SELECT actor__user_id, actor__name, COUNT(*) AS calls,
       SUM(content__duration_sec) AS duration_seconds
FROM touchpoints
WHERE snapshot_id = :snapshot_id AND event_type = 'call'
GROUP BY actor__user_id, actor__name;

SELECT title, raw_OPPORTUNITY, raw_CURRENCY_ID, responsible_user_id
FROM entities
WHERE snapshot_id = :snapshot_id AND entity = 'deal' AND entity_group = 'active';
```

### Полные файлы ZIP в отдельной базе

Скрипт [import_snapshot.py](../import_snapshot.py) импортирует готовый ZIP,
включая скачанный с Google Диска, в отдельную SQLite-базу. После скачивания
последнего нужного архива укажите его путь явно; скрипт не выбирает архив
автоматически и не обращается к Диску или Bitrix24:

```text
mise exec -- uv run --locked python -B scripts/import_snapshot.py "export/LEXS выгрузка из Битрикс24 на дату 2026-11-23 12-00.zip" --db data/sqlite3.db
```

Оба пути обязательны. Относительные пути считаются от текущего рабочего
каталога. База и родительские каталоги создаются при необходимости.
Используется только стандартная библиотека Python; `config.py`, `.env`,
store, state и registry не читаются и не изменяются. ZIP не распаковывается
на диск и не изменяется. Сообщения выводятся в терминал, файлы логов не создаются.
Бот и `sync.py` этот скрипт автоматически не вызывают.

В базе две постоянные таблицы; каждый архив добавляет новый снимок:

| Таблица | Поля и назначение |
|---|---|
| `snapshots` | `snapshot_id` из `manifest.export_id`, `snapshot_at`, время импорта `imported_at` (UTC), `archive_name`, `schema_version`, `status`, `is_complete`, число файлов `file_count`, отпечаток содержимого `content_sha256` |
| `snapshot_files` | `snapshot_id`, путь внутри ZIP `path`, полный исходный UTF-8 текст `content`, размер в байтах `size_bytes`, `sha256`, тип `entity`, ID `entity_id`, группа `entity_group` |

Ключ файла — `(snapshot_id, path)`. Все файлы архива, включая `manifest.json`,
сохраняются отдельными строками. Пустые каталоги строк не создают. Переводы
строк, Unicode и оформление карточек сохраняются; Markdown не разбирается
на поля CRM или отдельные касания. Тип (`deal` / `lead`), целочисленный ID
и группа (`active` / `completed` / `technical`) извлекаются из стандартных
имён и путей карточек. Для остальных файлов эти три поля равны `NULL`.
Одинаковые ID сделки и лида различаются по типу. JSONL, raw и аудио,
отсутствующие в ZIP, в базу не добавляются.

История добавляется без перезаписи: неизменившиеся карточки также получают
строку в каждом новом снимке. Повтор того же `export_id` с идентичными путями
и байтами файлов пропускается, даже если ZIP переименован или перепакован.
Изменившееся содержимое при прежнем `export_id` считается конфликтом;
старый снимок не заменяется. Частичные снимки сохраняются с исходными
`status=partial` и `is_complete=0`; полнота CRM заново не оценивается.

Перед записью проверяются UTF-8 всех файлов, JSON и обязательные поля
manifest, повторяющиеся и некорректные пути, читаемость/CRC содержимого ZIP.
Запись снимка и его файлов выполняется одной SQLite-транзакцией: при ошибке
новый снимок целиком откатывается. При ошибке первой записи может остаться
пустой файл БД. Чужая непустая база и неизвестная версия схемы отклоняются
без миграции. Ожидание блокировки SQLite ограничено 10 секундами.
Код выхода — `0` при добавлении или пропуске повтора, `1` при ошибке импорта,
`2` при неверных аргументах CLI.

Примеры запросов:

```sql
SELECT snapshot_id, snapshot_at, status, file_count
FROM snapshots ORDER BY snapshot_at;

SELECT s.snapshot_at, f.content
FROM snapshot_files AS f
JOIN snapshots AS s USING (snapshot_id)
WHERE f.entity = 'deal' AND f.entity_id = 123
ORDER BY s.snapshot_at;
```

База хранит те же чувствительные данные, что и ZIP, и не использует
ZIP-сжатие: с ростом истории размер увеличивается. Файлы `*.db` и `*.db-*`
исключены из Git. Очистки истории и устранения повторяющихся текстов нет.

## Касание

Схема — в [normalize.py](../normalize.py). Пример звонка:

```json
{
  "deal_id": 1234,
  "touchpoint_id": "call_991",
  "timestamp": "2026-07-15T14:32:10+03:00",
  "channel": "call",
  "event_type": "call",
  "direction": "in",
  "actor": {"type": "manager", "user_id": 17, "name": "Иванов И.И."},
  "responsible_user_id": 42,
  "client": {"contact_id": 555, "name": "Петров П."},
  "deal_stage_at_time": {"stage_id": "C1:PREPARATION", "name": "Подготовка"},
  "content": {"type": "transcript", "text": "Текст разговора",
              "duration_sec": 143, "recording_url": null,
              "transcript_status": "assemblyai"},
  "source": {"activity_id": 991, "file_ids": [512]}
}
```

`deal_id` содержит ID **и у лидов**: тип определяйте по файлу/контексту.
`deal_stage_at_time` вычисляется по истории на момент события или равен `null`.
`responsible_user_id` — ответственный за сущность, а `actor` определяется так:

| Событие | `touchpoint_id` | Источник actor |
|---|---|---|
| Звонок | `call_<activity_id>` | `RESPONSIBLE_ID` активности, при отсутствии — `AUTHOR_ID` |
| Сообщение ОЛ | `ol_<chat_id>_<msg_id>` | Отправитель через `classify_sender` |
| Комментарий | `comment_<id>` | `AUTHOR_ID` |
| Письмо / встреча | `act_<id>` | `AUTHOR_ID` |
| Задача | `task_<id>` | Исполнитель `RESPONSIBLE_ID`; постановщик — `content.created_by` |
| Смена стадии | `stage_<i>_<stage_id>` | `system` |

Основной сбор переписок читает все доступные сессии чата и их страницы.
В сыром `raw/<entity>_<id>.json` каждый элемент `ol_chats` содержит
`chat`, объединённые `messages` и список `session_ids`; старые raw могли не
содержать этого списка. ID сообщения остаётся `ol_<chat_id>_<msg_id>`:
сессия не меняет формат касания, JSONL и Markdown.
[Доступность и ограничения полноты](architecture.md#история-открытых-линий).

Для [обновления уже сохранённых переписок](operations.md#обновление-сохранённых-переписок)
предусмотрен `scripts/refresh_chats.py`. Его manifest имеет
`update_mode=CHAT_REFRESH`: состав карточек берётся из исходного manifest,
все переписки перечитываются, поля CRM и прочие касания сохраняются.
`snapshot_at` — время новой сборки; прежняя дата CRM остаётся в
`chat_refresh.crm_snapshot_at` и исходном coverage. Якорь `state.last_run`
не продвигается. Registry выбранных карточек указывает новый export_id,
чтобы индексы и структурированные источники оставались согласованными.

- `channel`: `call`, код ОЛ (`viber`, `telegram`, `whatsapp`, `site_chat`, `vk`,
  `instagram`, `facebook`, `avito`, `olx` и др.), `comment`, `email`, `meeting`, `task`, `crm`.
- `event_type`: `call`, `message`, `comment`, `email`, `meeting`, `task`, `stage_change`.
- `direction`: `in`, `out`, `internal`, `unknown`, `null`; `actor.type`:
  `manager`, `client`, `bot`, `system`, `unknown`; `content.type`: `text`, `transcript`, `meta`.
- `source`: `activity_id`, `chat_id` + `message_id`, `comment_id` или `task_id`;
  у звонков также `file_ids` и `stat_id: null` для совместимости схемы.
- Content звонка: телефон, длительность, пропуск, путь аудио, комментарий;
  запись получается по `file_ids` Диска, `recording_url` сохранён как `null`
  для совместимости схемы и не используется для скачивания.
  Задачи: описание, статус, дедлайн,
  дата закрытия. Стадии: `stage_from` / `stage_to`.

`transcript_status`: `assemblyai` — текст получен;
`no_recording` — нет подходящей записи; `no_transcript` — AssemblyAI не дал
текста; `pending` — получение отключено/не запрашивалось, без обещания фонового задания.

Индекс: `deal_id` **или** `lead_id`, `entity`, заголовок, даты, ответственный,
контакт, источник, страна, стадия, `closed`, группа, количества `touchpoints`,
`calls`, `ol_chats`, `tasks`, `fields`, при переносе — `reused`.
Все стандартные/пользовательские поля выгружаются, значения списков и справочников
разрешаются через метаданные. В карточке — «Поля сделки» / «Поля лида».

## Manifest и границы полноты

### Какие ZIP передавать ИИ

Для анализа состояния на дату обычно достаточно **последнего проверенного ZIP**
с нужным охватом. Архив содержит карточки целиком, а не только изменения
после прошлого запуска. В инкременте к текущей выборке добавляются пригодные
закрытые/технические сущности из registry/store; в `full` состав задаёт выборка.
Пропуск промежуточного ZIP сам по себе не создаёт разрыв в накопленных карточках
последнего снимка. Сохранность локальных store/registry важна для сборки инкремента,
но не зависит от того, какие архивы были переданы ИИ.

Для сравнения состояний на разные даты нужны соответствующие старые ZIP:
новый снимок не содержит прежние версии полей и ленты событий. Если событие
исчезло из источника или значение было изменено, его старая версия может
остаться только в прошлом архиве. Все архивы нужны лишь для анализа всех
сохранённых состояний; при объединении учитывайте дату снимка и тип/ID сущности,
иначе одни и те же карточки будут посчитаны многократно.

Полноту последнего ZIP проверяйте по manifest и ограничениям ниже.
При `REEXPORT_CLOSED_ON_CHANGE=False` закрытые карточки могут переноситься
из store без обновления даже после изменения в CRM. Это ограничение свежести
данных, которое не устраняется передачей ИИ всех ZIP.

### Поля manifest

| Поля | Смысл |
|---|---|
| `export_id`, `schema_version`, `snapshot_at`, `snapshot_timezone` | Идентификация/время |
| `export_type` | Всегда `FULL_SNAPSHOT` — накопленный снимок |
| `update_mode`, `previous_export_id`, `previous_snapshot_at`, `changed_since`, `overlap_from` | Способ получения (`FULL` / `INCREMENTAL`), прошлый якорь и окно |
| `countries`, `pipelines`, `coverage` | Страны, воронки; от старейшего объекта результата до снимка |
| `filter` | Даты, группы, источники, правила технических; `leads.enabled`; `per_entity.deals/leads`: `ids`, `limit`, `limit_reached` |
| `deals`, `leads` | Total, счётчики групп/файлов, ID, `groups.<group>.count/reused/ids`, ошибки; все группы, даже пустые |
| `errors`, `errors_count`, `skipped` | Ошибки и пропуски |
| `is_complete`, `status` | Нет зарегистрированных ошибок — `true` / `complete`, иначе `false` / `partial` |

**`FULL_SNAPSHOT` и `is_complete=true` не гарантируют охват всей CRM.** Лимиты,
отключённые группы/источники, пропуски и перехваченные ошибки источников сами
по себе не снимают флаг полноты. Проверяйте filter, coverage, skipped и логи.
Период manifest описывает настройки; фактическая выборка зависит от режима и
приоритета `DATE_FROM`. Оба типа сущностей проверяйте отдельно.
Незавершённая пагинация основной истории сессии отмечается как ошибка сущности,
но охват предыдущих сессий чата всё ещё имеет
[ограничения полноты](architecture.md#история-открытых-линий).
Также сопоставляйте флаги групп с фактическими `groups.<group>.ids`:
[перенос из текущей выборки](architecture.md#режимы-и-переиспользование)
может сохранить записи отключённой группы.

При пустом блоке `leads` текущий рендер может записать `deal_ids: []` вместо
`lead_ids: []`: тип определяется по записям индекса. Для пустого блока
ориентируйтесь на имя блока, `total` и `groups`, а не только на ключ списка ID.

При `REEXPORT_CLOSED_ON_CHANGE=False` перенесённые карточки могут не отражать
последующие изменения. Full ограничен выборкой, инкремент добавляет пригодные
старые закрытые из store. [Подробности](architecture.md#режимы-и-переиспользование).
