# Эксплуатация и восстановление

[Все документы](README.md) · [Запуск](setup.md) · [Форматы результата](data.md)

## Проверка кода

Перед изменением логики используйте [изолированные тесты](testing.md).
Они не требуют вебхука и рабочих данных. Запуск `sync.py` с лимитами в config
проверяет настоящий портал и перезаписывает часть локальных данных;
его побочные эффекты описаны в [setup.md](setup.md#команды-и-побочные-эффекты).

## Проверка результата

1. В `debug.log` проверьте фильтры, режим, ошибки и warning источников;
   прогресс — в `data/progress.json`.
2. В manifest сверьте status, errors, skipped, coverage, группы и
   `filter.per_entity`; `limit_reached=true` означает возможное ограничение.
   Учитывайте [границы полноты](data.md#manifest-и-границы-полноты).
3. Выборочно сопоставьте карточки, индекс и касания: actor/ответственный,
   время/стадия, текст, транскрипция, поля и группа; отдельно сделки и лиды.
4. Проверьте время/содержимое нового ZIP: он создаётся при включённом
   `MAKE_SNAPSHOT_ZIP` и непустом результате, JSONL в него не входят.

Snapshot пересоздаётся и ограниченным запуском. JSONL пишутся только для
непустых групп, поэтому старые могут остаться. Само наличие файла/архива
не подтверждает его актуальность.

## Диагностика скачивания аудио

При зависании прямого получения записи AssemblyAI выполните на сервере
из корня проекта, используя существующее окружение и `.env`:

```text
mise exec -- uv run --locked python -B scripts/diag_download.py --activity-ids 479980 480444
```

Это ID CRM-активностей звонков, а не ID сделок. Для других звонков замените
числа на `activity_id` из debug.log. Если известны ID файлов Диска:

```text
mise exec -- uv run --locked python -B scripts/diag_download.py --file-ids 345040 345668
```

Команды одинаковы на Windows, macOS и Linux. Скрипту нужны актуальные
`scripts/diag_download.py`, корневые `transcribe.py` и `logging_setup.py`; новые зависимости
не требуются. Доступ к Bitrix24 берётся из `B24_WEBHOOK` в окружении или `.env`.
При импорте config могут создаваться отсутствующие стандартные рабочие каталоги.

Если используется подготовленный архив диагностики, распакуйте его в корень
проекта: он создаёт отдельную папку `download_diagnostics/` со своими копиями
диагностических модулей и не заменяет рабочие модули сервера. Запуск:

```text
mise exec -- uv run --locked python -B download_diagnostics/run.py --activity-ids 479980 480444
```

Обёртка берёт config/.env и B24Client из родительского проекта; лог также
создаётся в его корне. Общие рабочие каталоги и правила доступа те же.

За один запуск разрешены до четырёх ID. Скрипт вызывает только чтение
`crm.activity.get` и `disk.file.get`; для активности проверяется первый файл,
как в основном потоке транскрибации. Затем для каждой свежей ссылки сравниваются:

- обычный GET с чтением не более 64 КиБ;
- HTTP Range первых 8 КиБ и 8 КиБ со смещения 16384 (с учётом размера файла);
- GET с `Connection: close` и `Accept-Encoding: identity`;
- при наличии curl — независимое чтение Range до 64 КиБ без перенаправлений,
  с ограничением размера и времени. Код 63 означает превышение лимита размера,
  а не сам по себе сетевой сбой.

Аудио обрабатывается в памяти и не сохраняется. Скрипт не обращается к AssemblyAI,
не создаёт транскрипции и не меняет store, registry, state или progress.
Для Python-пробы тайм-аут соединения — 8 с, ожидания данных — 10 с,
бюджет 30 с проверяется между чтениями; блокирующий запрос может завершиться
позже этого бюджета. curl ограничен 12 с (ожидание subprocess — 16 с).
Метаданные Bitrix24 используют обычные тайм-ауты и повторы из config, поэтому
при недоступности API весь запуск может длиться заметно дольше.

Результат — отдельный `diag_download_<UTC-время>_<PID>.log` в корне проекта.
Скрипт печатает его путь при завершении; можно задать новое имя через
`--log server_download.log`. Существующий лог не перезаписывается.
Запись ведётся во временный `.log` рядом с результатом и завершается атомарным
переименованием; Ctrl+C также сохраняет собранную часть.
Общие debug.log и error.log не открываются.

Отчёт содержит версии среды, наличие proxy-переменных без их значений,
HTTP-статусы, тип/длину содержимого, диапазоны, время до заголовков/первых данных,
число реально прочитанных байтов и класс исключения. Ссылки, ключи, cookie,
имена файлов/клиентов, тексты активностей и аудио в него не включаются.
Для сетевых ошибок не записывается произвольный текст исключения.

`file_complete` — прочитан весь ответ известной длины; `sample_complete` —
достигнут лимит пробы, что не доказывает скачивание полного большого файла.
`range_honored=true` подтверждает совпадение ответа 206 с запрошенным диапазоном.
Если Range успешен, а stream зависает после частичных данных, сравните тот же
отчёт с другой машины: это помогает отделить выдачу файла от сетевого маршрута.
Код завершения: 0 — обычные stream-пробы успешны, 1 — обнаружены ошибки stream
или получения метаданных (лог сохранён), 2 — сбой запуска, 130 — Ctrl+C.
Необязательные варианты и Range оценивайте по отдельным записям `probe`.

## Логирование

Выгрузка, бот и утилиты обслуживания используют Loguru. При запуске создаются два
UTF-8 файла в корне проекта (пути `DEBUG_LOG_PATH` / `ERROR_LOG_PATH` в config):

| Файл | Содержимое |
|---|---|
| `debug.log` | DEBUG и выше: режим и фильтры выгрузки, ID и счётчики сущностей, этапы транскрибации, повторы запросов, предупреждения и ошибки |
| `error.log` | ERROR и CRITICAL: ошибки сущностей, окончательные сбои скачивания/транскрибации, аварийное завершение процесса; traceback при неожиданных исключениях |

Каждая запись содержит время, уровень, PID, модуль, функцию и строку кода.
Ошибки повторяются в обоих файлах, чтобы сохранить контекст в `debug.log`.
Неудача прямой ссылки с переходом на upload — WARNING; она остаётся в debug.
Обычный ход запросов, тела ответов, тексты общения, названия сделок и ФИО
не добавляются в диагностические сообщения. INFO/DEBUG сторонних библиотек
отфильтрованы, WARNING и выше направляются в эти же файлы.
URL, известные ключи доступа и параметры авторизации маскируются и в сообщениях,
и в цепочках исключений; значения локальных переменных в traceback не выводятся.
Это не обезличивает произвольный текст ошибки стороннего сервиса:
перед передачей логов другому человеку просмотрите их содержимое.

Настройка выполняется через `logging_setup.run_cli` в точках входа.
При использовании модулей из своего скрипта вызовите `configure_logging()`.
Автономные `scripts/snapshot_sqlite.py`, `scripts/import_snapshot.py` и
`scripts/source_sqlite.py` не загружают настройки
приложения и выводят результат/ошибки только в терминал;
см. [экспорт в SQLite](data.md#sqlite).
Обычная выгрузка при `SNAPSHOT_SQLITE_ENABLED=True` после создания ZIP
добавляет его в `SNAPSHOT_SQLITE_PATH`. Ошибка импорта откатывает этот снимок
в БД, записывается в лог и `progress.json` (`sqlite_status=error`, тип в
`sqlite_error`); ZIP и завершение state/registry сохраняются. Повторить импорт
можно вручную из готового архива. При успехе `sqlite_status=added/existing`,
`sqlite` содержит имя БД. Без ZIP (пустая выборка или отключённая архивация)
импорт не выполняется. Загрузки SQLite на Google Диск этим изменением нет.
Логи дописываются между запусками; повторная настройка не дублирует обработчики.
Бот и дочерний процесс выгрузки пишут в общие файлы с PID. Автоматической ротации нет:
размер файлов контролируется при обслуживании; для переноса/очистки остановите
бота и выгрузку. Эти файлы исключены из Git маской `*.log`.

## Хранение и безопасность

Перед обслуживанием остановите писателей и сохраните согласованную копию
`data/` и нужных ZIP; raw, тексты и аудио — для восстановления без повторных
запросов. Store хранит последние версии. Store/registry/state не везде пишутся
атомарно: после обрыва проверяйте читаемость и согласованность четырёх файлов
store для каждой затронутой сущности, а также state и registry.
Метаданные сделок/лидов обновляются атомарно; это не защищает остальные файлы.
Не запускайте ручную выгрузку, выгрузку из бота и служебные скрипты одновременно
над одними данными: PID-файл бота не защищает прямой запуск `sync.py`.

Переписки, персональные данные, `.env`, `credentials/`, `data/`, `raw/`,
`export/`, `audio/`, `transcripts/`, логи и окружения `.venv/` / `venv/` не публикуются. Маска `*.json`
также исключает JSON из Git. Авторизованные URL Диска секретны: прямой режим
передаёт их AssemblyAI, upload передаёт аудио. Перед отправкой архива проверяйте
получателя и доступ к данным.

## Обслуживание

Служебные точки входа находятся в `scripts/`; команды ниже выполняются из корня
проекта. Python-функции работы с SQLite остаются в корневых модулях
`import_snapshot.py`, `source_sqlite.py`, `snapshot_sqlite.py`, чтобы сохранять
их использование основным потоком и другими Python-модулями.

Команды изменения данных выполняются вручную после резервирования:

| Команда | Назначение |
|---|---|
| `mise exec -- uv run --locked python -B scripts/snapshot_sqlite.py "путь/к/снимку.zip" --db data/sqlite3_snapshots.db` | Добавить конечные карточки в структурированную БД с устранением повторов. Можно передать несколько ZIP; каждый фиксируется отдельной транзакцией. [Схема и запросы](data.md#база-конечных-карточек-без-повторов) |
| `mise exec -- uv run --locked python scripts/source_sqlite.py --data-dir data --export-dir export --manifest export/snapshot/manifest.json --db data/sqlite3_structured.db` | Разложить исходные поля и нормализованные касания в SQLite. Выполнять на согласованном комплекте одного завершённого запуска при остановленных писателях; [схема и источники](data.md#структурированная-база-из-первоисточников) |
| `mise exec -- uv run --locked python scripts/import_snapshot.py "путь/к/снимку.zip" --db data/sqlite3.db` | Импортировать готовый ZIP в SQLite без API; добавить снимок, сохранив историю. [Схема и проверки](data.md#sqlite) |
| `mise exec -- uv run --locked python scripts/refresh_names.py` | Обновить справочники через API, имена/поля и служебную страну в store, перерендерить карточки, snapshot, JSONL и ZIP; без повторной выгрузки активностей/транскрибации |
| `mise exec -- uv run --locked python scripts/refresh_names.py --offline` | Та же перезапись из кэшей без API; новых имён с портала не будет |
| `mise exec -- uv run --locked python scripts/recover_registry.py` | Дописать отсутствующие записи registry из полных комплектов store, без API; существующие не исправляет |
| `mise exec -- uv run --locked python scripts/diag_filter.py` | Диагностика фильтра сделок с запросом API |
| `mise exec -- uv run --locked python scripts/diag_fields.py` | Диагностика API-полей, включая `crm.deal.userfield.list`, `crm.item.fields` вне основного потока |

Refresh не меняет state/registry и не обновляет историю общения. Offline требует
`data/users_cache.json`; без метаданных поля обновляются упрощённо. Пользователи
загружаются без фильтра активности, для разрешения имён уволенных также есть
точечные запросы `LazyUserMap`.

Recovery не восстанавливает повреждённые/отсутствующие артефакты и ставит
**текущую** `SCHEMA_VERSION`: заранее проверьте соответствие схемы store.
После восстановления выполните обычный проход и проверьте результат.
Ошибки обработки из state повторяются в следующем инкременте; для пересборки
всей истории после смены схемы нужен full с нужным охватом.
Не удаляйте store/registry ради «чистого» запуска.

Для проверки снимка используйте `export/snapshot/manifest.json` и карточки
в `export/snapshot/{Сделки,Лиды}/`. Каталог `export/deals/` основной поток
не создаёт. Автотесты в `tests/` проверяют искусственные снимки и не оценивают
полноту уже полученного рабочего архива.

## Telegram-бот

[bot.py](../bot.py) — основной пульт запуска выгрузки. aiogram 3 входит
в зависимости проекта и устанавливается через `mise run setup`.
Задайте `TG_BOT_TOKEN` и `TG_CHAT_ID` (один ID чата или несколько через запятую)
в файле `.env` рядом с `config.py`
([загрузка секретов](setup.md#окружение-и-доступ)), затем:

```text
mise run start
```

`/start` в разрешённом чате показывает кнопку. Бот запускает `sync.py` без
аргументов тем же Python и с текущим config, хранит PID в `data/sync.lock`,
логи — в общих `debug.log` / `error.log`, опрашивает progress каждые **5 с**.
Отдельный `data/sync_run.log` больше не создаётся; старый файл не удаляется.
ZIP до 45 МиБ отправляет в чат, для большего показывает серверный путь.

После завершения, даже с ошибкой, выбирается самый новый ZIP из export по mtime.
Если новый не создан, бот может отправить старый: сверяйте время и manifest.

На Linux бот может работать через systemd. Локальный `bitrix-export.service`
исключён из Git и привязан к серверу. Для своего сервера задайте `User`,
`WorkingDirectory`, `ExecStart` (абсолютные пути Python из `.venv` и bot.py),
запуск после сети и перезапуск при сбое. Секреты загружает `config.py` из `.env`
рядом с ним. Это сервис бота,
не расписание выгрузки. Изменение/запуск сервиса — отдельная операция на сервере.
