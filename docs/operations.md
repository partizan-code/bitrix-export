# Эксплуатация и восстановление

[Все документы](README.md) · [Запуск](setup.md) · [Форматы результата](data.md)

## Проверка кода

Перед изменением логики используйте [изолированные тесты](testing.md).
Они не требуют вебхука и рабочих данных. Запуск `sync.py` с лимитами в config
проверяет настоящий портал и перезаписывает часть локальных данных;
его побочные эффекты описаны в [setup.md](setup.md#команды-и-побочные-эффекты).

## Проверка результата

1. В `debug.log` проверьте фильтры, режим, ошибки и warning источников;
   прогресс — в `data/progress.json`.
2. В manifest сверьте status, errors, skipped, coverage, группы и
   `filter.per_entity`; `limit_reached=true` означает возможное ограничение.
   Учитывайте [границы полноты](data.md#manifest-и-границы-полноты).
3. Выборочно сопоставьте карточки, индекс и касания: actor/ответственный,
   время/стадия, текст, транскрипция, поля и группа; отдельно сделки и лиды.
4. Проверьте время/содержимое нового ZIP: он создаётся при включённом
   `MAKE_SNAPSHOT_ZIP` и непустом результате, JSONL в него не входят.

Snapshot пересоздаётся и ограниченным запуском. JSONL пишутся только для
непустых групп, поэтому старые могут остаться. Само наличие файла/архива
не подтверждает его актуальность.

## Логирование

Выгрузка, бот и утилиты обслуживания используют Loguru. При запуске создаются два
UTF-8 файла в корне проекта (пути `DEBUG_LOG_PATH` / `ERROR_LOG_PATH` в config):

| Файл | Содержимое |
|---|---|
| `debug.log` | DEBUG и выше: режим и фильтры выгрузки, ID и счётчики сущностей, этапы транскрибации, повторы запросов, предупреждения и ошибки |
| `error.log` | ERROR и CRITICAL: ошибки сущностей, окончательные сбои скачивания/транскрибации, аварийное завершение процесса; traceback при неожиданных исключениях |

Каждая запись содержит время, уровень, PID, модуль, функцию и строку кода.
Ошибки повторяются в обоих файлах, чтобы сохранить контекст в `debug.log`.
Неудача прямой ссылки с переходом на upload — WARNING; она остаётся в debug.
Обычный ход запросов, тела ответов, тексты общения, названия сделок и ФИО
не добавляются в диагностические сообщения. INFO/DEBUG сторонних библиотек
отфильтрованы, WARNING и выше направляются в эти же файлы.
URL, известные ключи доступа и параметры авторизации маскируются и в сообщениях,
и в цепочках исключений; значения локальных переменных в traceback не выводятся.
Это не обезличивает произвольный текст ошибки стороннего сервиса:
перед передачей логов другому человеку просмотрите их содержимое.

Настройка выполняется через `logging_setup.run_cli` в точках входа.
При использовании модулей из своего скрипта вызовите `configure_logging()`.
Логи дописываются между запусками; повторная настройка не дублирует обработчики.
Бот и дочерний процесс выгрузки пишут в общие файлы с PID. Автоматической ротации нет:
размер файлов контролируется при обслуживании; для переноса/очистки остановите
бота и выгрузку. Эти файлы исключены из Git маской `*.log`.

## Хранение и безопасность

Перед обслуживанием остановите писателей и сохраните согласованную копию
`data/` и нужных ZIP; raw, тексты и аудио — для восстановления без повторных
запросов. Store хранит последние версии. Store/registry/state не везде пишутся
атомарно: после обрыва проверяйте читаемость и согласованность четырёх файлов
store для каждой затронутой сущности, а также state и registry.
Метаданные сделок/лидов обновляются атомарно; это не защищает остальные файлы.
Не запускайте ручную выгрузку, выгрузку из бота и служебные скрипты одновременно
над одними данными: PID-файл бота не защищает прямой запуск `sync.py`.

Переписки, персональные данные, `.env`, `credentials/`, `data/`, `raw/`,
`export/`, `audio/`, `transcripts/`, логи и venv не публикуются. Маска `*.json`
также исключает JSON из Git. Авторизованные URL Диска секретны: прямой режим
передаёт их AssemblyAI, upload передаёт аудио. Перед отправкой архива проверяйте
получателя и доступ к данным.

## Обслуживание

Команды изменения данных выполняются вручную после резервирования:

| Команда | Назначение |
|---|---|
| `python refresh_names.py` | Обновить справочники через API, имена/поля и служебную страну в store, перерендерить карточки, snapshot, JSONL и ZIP; без повторной выгрузки активностей/транскрибации |
| `python refresh_names.py --offline` | Та же перезапись из кэшей без API; новых имён с портала не будет |
| `python recover_registry.py` | Дописать отсутствующие записи registry из полных комплектов store, без API; существующие не исправляет |
| `python diag_filter.py` | Диагностика фильтра сделок с запросом API |
| `python diag_fields.py` | Диагностика API-полей, включая `crm.deal.userfield.list`, `crm.item.fields` вне основного потока |

Refresh не меняет state/registry и не обновляет историю общения. Offline требует
`data/users_cache.json`; без метаданных поля обновляются упрощённо. Пользователи
загружаются без фильтра активности, для разрешения имён уволенных также есть
точечные запросы `LazyUserMap`.

Recovery не восстанавливает повреждённые/отсутствующие артефакты и ставит
**текущую** `SCHEMA_VERSION`: заранее проверьте соответствие схемы store.
После восстановления выполните обычный проход и проверьте результат.
Ошибки обработки из state повторяются в следующем инкременте; для пересборки
всей истории после смены схемы нужен full с нужным охватом.
Не удаляйте store/registry ради «чистого» запуска.

Для проверки снимка используйте `export/snapshot/manifest.json` и карточки
в `export/snapshot/{Сделки,Лиды}/`. Каталог `export/deals/` основной поток
не создаёт. Автотесты в `tests/` проверяют искусственные снимки и не оценивают
полноту уже полученного рабочего архива.

## Telegram-бот

[bot.py](../bot.py) — основной пульт запуска выгрузки. Для него требуется aiogram 3,
отсутствующий в requirements: `python -m pip install "aiogram>=3,<4"` в том же
окружении. Самому процессу `sync.py` он не нужен.
Задайте `TG_BOT_TOKEN` и `TG_CHAT_ID` (один ID чата или несколько через запятую)
в файле `.env` рядом с `config.py`
([загрузка секретов](setup.md#окружение-и-доступ)), затем:

```text
python bot.py
```

`/start` в разрешённом чате показывает кнопку. Бот запускает `sync.py` без
аргументов тем же Python и с текущим config, хранит PID в `data/sync.lock`,
логи — в общих `debug.log` / `error.log`, опрашивает progress каждые **5 с**.
Отдельный `data/sync_run.log` больше не создаётся; старый файл не удаляется.
ZIP до 45 МиБ отправляет в чат, для большего показывает серверный путь.

После завершения, даже с ошибкой, выбирается самый новый ZIP из export по mtime.
Если новый не создан, бот может отправить старый: сверяйте время и manifest.

На Linux бот может работать через systemd. Локальный `bitrix-export.service`
исключён из Git и привязан к серверу. Для своего сервера задайте `User`,
`WorkingDirectory`, `ExecStart` (абсолютные пути Python из venv и bot.py),
запуск после сети и перезапуск при сбое. Секреты загружает `config.py` из `.env`
рядом с ним. Это сервис бота,
не расписание выгрузки. Изменение/запуск сервиса — отдельная операция на сервере.
