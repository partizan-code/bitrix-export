# Сверка запросов Bitrix24

[Все документы](README.md) · [Работа с MCP](bitrix-api.md) · [Архитектура](architecture.md)

Дата аудита: 24 ноября 2026 года. При первоначальной сверке проверена рабочая
версия, включая существовавшие незакоммиченные изменения. Это был статический
анализ без изменения кода и запуска тестов. Последующие исправления отмечены
ниже; испытания рабочего портала не выполнялись.

## Ход устранения замечаний

1. **24 ноября 2026, шаг 1 — пагинация последней сессии (часть первого P1).**
   `get_chat_history` обходит страницы по `hasNextPage` и паре `nextId/nextDate`,
   после первой страницы фиксирует `SESSION_ID`, объединяет пользователей,
   исключает дубли сообщений и сортирует одинаковое время по числовому ID.
   Некорректные ответы, повтор курсора и предел
   `OPENLINES_SESSION_MAX_PAGES` дают `BitrixError(INCOMPLETE_HISTORY)`.
   Ошибка API после первой страницы также передаётся наружу без IM fallback:
   штатный обработчик отмечает ошибку сущности, продолжает остальные и
   сохраняет её ID для повтора в следующем инкременте обычного прогона.
   Проверки на синтетических данных описаны в [testing.md](testing.md).
   На этом шаге оставались предыдущие сессии чата и замечания к IM fallback.
   Первый P1 пока не закрыт целиком.
2. **24 ноября 2026, шаг 2 — полное удаление IM fallback.** По решению
   пользователя удалены `_history_via_im`, переход на `im.dialog.messages.get`
   и соответствующие моки. Ошибка `imopenlines.session.history.get` на любой
   странице теперь передаётся в штатную обработку ошибок сущности: manifest
   становится `partial`, остальные сущности продолжаются, в обычном прогоне
   ID сохраняется в state для повтора. Scope `im` больше не требуется.
   [Документация IM](https://apidocs.bitrix24.ru/api-reference/chats/messages/im-dialog-messages-get.html)
   направляет за историей открытых линий к `imopenlines.session.history.get`;
   универсальный fallback она не устанавливает. Замечание к IM закрыто
   удалением этого пути. **Остаётся:** охват предыдущих сессий через
   документированные возможности API открытых линий.
3. **24 ноября 2026, шаг 3 — удаление неиспользуемых веток звонков и лишнего повтора.**
   Удалены скачивание по `recording_url`, альтернативные ID из `stat_id` и
   повторный запуск `load_users` с тем же запросом после ошибки.
   Записи звонков берутся по `file_ids` Диска, ID звонка — `activity_id`.
   Поля `recording_url/stat_id` остаются `null` в JSON для совместимости,
   формат карточек и имена файлов сохраняются. Повторы `B24Client` действуют;
   при их исчерпании ошибка загрузки пользователей передаётся наружу.
   Контракт [user.get](https://apidocs.bitrix24.ru/api-reference/user/user-get.html)
   сверён через MCP, сам запрос без фильтра и его пагинация не менялись.
4. **24 ноября 2026, шаг 4 — все доступные сессии в основном экспорте.**
   Общий алгоритм списка перенесён из эксперимента в `fetch_openlines.py`.
   `OpenLinesHistory` загружает индекс один раз за прогон, объединяет чаты
   текущих CRM-привязок и связей индекса, читает все SESSION_ID и все страницы.
   Полные истории используются повторно между сделками/лидами; raw содержит
   `session_ids`. Отказ списка/привязок, недоступная сессия и лимиты дают ошибку
   сущности, а не успешную неполную историю. Поиск MCP для `crm.chat.get`
   вернул нерелевантный метод; прочитана карточка точного имени, контракт
   согласован. Все три метода повторно сверены через MCP. Формат карточек
   сохранён. Ограничения прав, тарифа и переноса из store остаются:
   [алгоритм](architecture.md#история-открытых-линий),
   [предложение обновления старых данных](operations.md#обновление-сохранённых-переписок-предлагаемый-порядок).

## Охват и метод

Для отдельного эксперимента добавлен

в основной модуль и используется также `sync.py`. Скрипт отдельно учитывает неполноту,
старые добавления и сообщения, поступившие после исходного снимка.

Поиск по Python-файлам и чтение AST первоначально обнаружили 23 разных REST-метода.
После перехода транскрибации только на AssemblyAI осталось 22 метода,
после удаления IM fallback — 21; с экспериментальным скриптом — 22.
Реестр и рекомендации ниже обновлены
с учётом удаления этих источников.
Учтены динамические `crm.{entity}.fields` для сделок и лидов, вызовы в

Карточки всех 23 методов прочитаны через MCP. Для смешанной карточки задач,
справочников, пагинации чатов, лимитов и рекомендаций по производительности
дополнительно использованы официальные веб-страницы. `rest.batch` изучен
как вариант оптимизации; сейчас проект его не вызывает.

`.env`, `.env.dev`, логи и выгрузки не читались. Запросы к рабочему порталу,
скачивание аудио и вызовы AssemblyAI не выполнялись. Права, тариф, версия

## Ошибки и риски корректности

### P1. История открытой линии выгружается частично — исправлено для доступных сессий

На момент аудита `fetch_openlines.get_chat_history` делал один запрос
по `CHAT_ID` и получал по умолчанию 50 сообщений последней сессии; код
игнорировал `hasNextPage`, `nextId`, `nextDate`. При длинной сессии пропускались
старые сообщения, при нескольких сессиях — предыдущие сессии. Успешный
ответ не включал fallback. [Контракт истории сессии](https://apidocs.bitrix24.ru/api-reference/imopenlines/openlines/sessions/imopenlines-session-history-get.html).

Предложение: разделить получение всех страниц конкретной сессии и сбор
истории всего чата. Для сессии передавать курсоры `LAST_ID/LAST_DATE`, пока
есть следующая страница. Для старых сессий нужен отдельно подтверждённый
источник истории; один цикл страниц последней сессии проблему не решает.
Не предполагать, что доступ к CRM автоматически даёт доступ к истории через IM.

**Состояние после шага 1:** пагинация одной сессии реализована и сверена
повторно через MCP и официальную страницу метода. Осталось обеспечить историю
предыдущих сессий. Успех этого метода по-прежнему означает завершение одной
сессии, а не подтверждённую полноту чата.

**Состояние после шага 4:** основной путь собирает все видимые сессии и страницы.
Сессии, скрытые правами, и обращения после начала загрузки индекса не гарантируются.
Ранее сохранённые карточки не мигрируются автоматически; отдельное обновление
переписок предложено в [инструкции](operations.md#обновление-сохранённых-переписок-предлагаемый-порядок).

### P1. Запасная загрузка IM — закрыто удалением

На момент аудита запасной путь имел ошибки лимита, курсора, направления
обхода и учёта неполноты. На шаге 2 этот путь полностью удалён;
предложения по его исправлению больше не применяются. Ошибки истории
сессии теперь передаются наружу с первой страницы.

### P2. Повторы не учитывают ресурсную блокировку метода

`B24Client._call` (`api_client.py:77–123`) обрабатывает любой HTTP 429 до
чтения JSON. Поэтому теряются конкретный код ошибки и её описание; ветка
`OPERATION_TIME_LIMIT` ниже недостижима для такого ответа. Пять попыток
с паузами 1+2+4+8+16 секунд могут закончиться раньше снятия блокировки.

Предложение: учитывать JSON ошибки и последнее известное
`time.operating_reset_at`, откладывать заблокированный метод в пределах
явного бюджета ожидания. Отдельно сохранить увеличивающиеся задержки
для ограничения интенсивности. [Правила лимитов и повторов](https://apidocs.bitrix24.ru/limits.html).

Пауза 0,2 секунды после ответа также не гарантирует допустимую интенсивность:
при быстрых ответах цикл превышает 2 запроса в секунду для обычного облачного
тарифа. Фактический тариф и общий трафик с того же IP не проверялись.

### P2. HTTP-ошибка с JSON может выглядеть как пустой результат

После разбора JSON `_call` проверяет только наличие `error`, но не успешность
HTTP-статуса и не структуру ответа (`api_client.py:93–130`). Например,
JSON от шлюза со статусом 502 без ключа `error` возвращается как успех;
`result()` превращает его в `None`, а `call_list()` — в пустую выборку.
Это вывод по коду, а не наблюдение на рабочем портале.

Предложение: проверить HTTP-статус и ожидаемую форму ответа, различать
временные сетевые ошибки, ошибки протокола и успешный пустой результат.
В `call_list` добавить защиту от повторяющегося/некорректного `next`, чтобы
не получать бесконечный цикл при некорректном ответе.

### P2. Запрос одного ID обходит условия отбора

При одном ID `get_deals` и `get_leads` сразу выполняют `get`
(`fetch_deals.py:49–52`, `fetch_leads.py:44–46`), не проверяя уже построенный
фильтр дат; для сделки теряется также фильтр `CLOSED`. Поэтому выборка одного
и нескольких ID имеет разную семантику. Сам вызов `get` корректен, это ошибка
локального отбора. Предложение: использовать `list` с тем же фильтром либо
применять все условия к полученной сущности, сохраняя согласованную семантику.

### P2. Недоступный источник и отсутствующие данные смешиваются

`get_deal_chats`, `get_deal_tasks` перехватывают `BitrixError` и возвращают
пустой список. Замечание к возврату частичной истории из IM устранено на шаге 2.
`process_entity` не получает отдельного признака ошибки источника. Ошибка
scope/прав может выглядеть как отсутствие касаний и не попасть в учёт
ошибок сущности. Предложение: сохранить продолжение выгрузки, но передавать
статус источника и отражать неполноту в результате и механизме повторов.

`LazyUserMap._fetch` и `ContactBook.name` (`users.py:103–129,155–167`) также
навсегда кэшируют временный сбой как отсутствие пользователя/имени контакта.
Нужно отличать подтверждённое отсутствие от временной ошибки и дать отрицательному
кэшу срок действия или сброс после восстановления доступа.

## Возможности оптимизации и уточнения

1. **Останавливать выборку по лимиту.** `DEALS_LIMIT/LEADS_LIMIT` применяются
   срезом после `call_list`, уже загрузившего все страницы. Для полного режима
   можно завершать сбор после нужного количества записей. Для объединения
   инкрементальных выборок предварительно сохранить сортировку и дедупликацию.
2. **Не запрашивать одинаковые справочники дважды.** `load_stages` и
   `load_categories` отдельно вызывают одинаковый `crm.category.list`.
   Передавать список воронок обеим функциям. Дополнительный повтор того же
   `user.get` в `load_users` после любого исключения удалён на шаге 3;
   повторы клиента сохранены.
3. **Уменьшить объём справочника пользователей.** Для имён сейчас используются
   только ID, ФИО и должность; их можно явно перечислить в `select`.
   Точечный `user.get` в `LazyUserMap._fetch` использует верхнеуровневый `ID`, тогда
   как текущая документация описывает `filter.ID`. Перейти на документированный
   вариант и обязательно проверять совпадение возвращённого ID. Поддержка
   старого варианта на конкретном портале не проверялась. Метод не возвращает
   ботов и пользователей открытых линий; их нельзя рассчитывать разрешить
   этим дозапросом. [Документация user.get](https://apidocs.bitrix24.ru/api-reference/user/user-get.html).
4. **Рассмотреть batch для независимых запросов.** Подходящие кандидаты —
   справочники, добор `crm.activity.get` и метаданных файлов. HTTP-метод —
   `batch`, до 50 команд, с разбором `result_error/result_next` каждой команды.
   Повторять только неуспешные команды, сохранять привязку к сущностям.
   Batch не отменяет ресурсные лимиты. [Официальный контракт batch](https://apidocs.bitrix24.ru/settings/how-to-call-rest-api/batch.html).
5. **Выбирать большие списки без повторного подсчёта total.** Рассмотреть
   отдельный обход по `ID ASC`, `>ID`, `start=-1` для совместимых методов.
   Текущий `call_list` перезаписывает `start` нулём, поэтому одной передачи
   параметра недостаточно. Поддержку проверять отдельно; на REST 3.0 этот
   способ автоматически не переносится. В `scripts/diag_filter.py` подсчёт
   `total` является целью диагностики и должен сохраниться.
   [Рекомендации по большим выборкам](https://apidocs.bitrix24.ru/settings/performance/huge-data.html).
6. **Уточнить полноту файлов и акторов.** Дела могут возвращать WebDAV-вложения,
   комментарии и сообщения — файлы, которые текущая нормализация не включает
   в касания. Это ограничение охвата, а не доказательство ошибки `disk.file.get`.
   `RESPONSIBLE_ID` дела обозначает ответственного за дело; для сторонних
   телефоний соответствие реальному участнику звонка нужно подтверждать
   отдельно. Поля типа пользователя/коннектора следует сохранять при разборе
   истории, чтобы внешний участник не становился менеджером только по наличию имени.
7. **Планировать миграцию REST отдельно.** Ряд CRM-методов помечен deprecated,
   что не означает прекращение их работы. Карточка MCP `tasks.task.list`
   смешивает `pagination/result.items` REST 3.0 и `start/result.tasks`
   текущего вызова. Не менять параметры без миграции адреса, схемы и моков.
   Поле `CREATED_BY_ID` в `TASK_SELECT` не подтверждено списком полей задач;
   документирован постановщик `createdBy` / `CREATED_BY`. Уточнить и удалить
   лишнее поле при отдельной правке. [Контракт текущих задач](https://apidocs.bitrix24.ru/api-reference/tasks/tasks-task-list.html),
   [поля ответа](https://apidocs.bitrix24.ru/api-reference/tasks/fields.html).

## Рекомендуемый порядок работ и проверки

Охват предыдущих доступных сессий реализован на шаге 4; для старых карточек
нужна отдельная пересборка переписок. Затем обработка HTTP/ресурсных лимитов, статусы недоступных источников,
отрицательные кэши и одинаковую семантику фильтров. После этого сокращать
запросы по измерениям: ранний лимит, общие справочники, batch и обход по ID.
Общий план ускорения остаётся в [roadmap.md](roadmap.md).

Для будущих исправлений нужны изолированные сценарии: несколько страниц
и сессий чата; сообщения в разном порядке;
дубликаты и повтор курсора; достижение лимита страниц;
HTTP 429 с `OPERATION_TIME_LIMIT`, 503 с `QUERY_LIMIT_EXCEEDED`, 502 с JSON
без `error`; один и несколько ID с теми же датами/статусами; временный сбой
справочника и последующее восстановление. Для оптимизаций дополнительно
проверить число HTTP-вызовов и неизменность состава касаний на моках.

Кроме отмеченных шагов 1–4, приведённые предложения не реализованы.
Реальная проверка прав, охвата и производительности требует отдельного
разрешения на конкретный запуск
рабочего API. Формат карточек, включая подпись «Страна», менять не требуется.
